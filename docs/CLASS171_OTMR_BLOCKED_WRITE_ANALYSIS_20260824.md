## Evidence and offset convention

The HHD trace is authoritative for Analyser.exe writes, recorder reads, port
operations, and timing. The OTMR raw capture independently confirms the
software-side recorder bytes and fragmentation:

- `TestData/HHD_Serial_Trace_20260824_143201.txt`
- `TestData/OTMR_RAW_CAPTURE_20260824.txt`

Offsets in this document and the CSV are zero-based offsets in the complete
frame. Payload offsets are explicitly labelled and start immediately after the
`02` at frame offset `0x008`; therefore `frame offset = payload offset + 0x009`.

The complete byte-for-byte table is
[`CLASS171_OTMR_BLOCKED_WRITE_OFFSETS_20260824.csv`](CLASS171_OTMR_BLOCKED_WRITE_OFFSETS_20260824.csv).
It has one row for every byte of every blocked TX and contains the same-offset
RX/TX values, changed/unchanged result, required classification, and (where a
byte is copied or modified after an insertion/deletion) its aligned source RX
offset and value. It is reproducible with:

```powershell
& .\tools\Analyze-OtmrBlockedWrites.ps1 -WriteOffsetCsv
```

## Proven frame and check-byte rules

For the captured data-page writes:

| Frame offset | Meaning |
|---:|---|
| `0x000` | `01`, protocol framing (SOH) |
| `0x001` | write command/page index, `01` through `06` |
| `0x002` | `00`, constant in all compared messages |
| `0x003` | page index, `01` through `06` |
| `0x004..0x006` | copied from the corresponding current-recorder RX header |
| `0x007` | payload length (`FF` for pages 1-5, `C6` for page 6) |
| `0x008` | `02`, protocol framing (STX) |
| `0x009..` | payload |
| third-last | `03`, protocol framing (ETX) |
| second-last | payload check byte |
| last | `04`, protocol framing (EOT) |

The check byte is not XOR and is not a multi-byte CRC. It is:

`check = sum(all payload bytes between STX and ETX) modulo 256`

This rule reproduces the observed check byte for all 19 Analyser.exe HHD Write
Requests and every complete software-side RX frame in the supplied capture.
For the six large writes the calculated/observed checks are respectively `8E`,
`55`, `6B`, `74`, `00`, and `40`.

## Trigger RX versus payload-source RX

The immediate recorder reply gates the next page, but the large TX payload is
derived from a cached page read earlier in the interrogation. These are distinct
relationships:

| HHD TX | Immediate trigger/position | Payload source from current recorder |
|---|---|---|
| `000301` | completion of RX `01 0C` | RX `01 0C` header/transaction |
| `000312` | immediately after `000301` and purge | earlier RX `01 02`, page/index 1 |
| `000335` | RX `01 0D ... payload 01` | earlier RX `01 04`, page/index 2 |
| `000357` | RX `01 0E ... payload 02` | earlier RX `01 06`, page/index 3 |
| `000378` | RX `01 0F ... payload 03` | earlier RX `01 08`, page/index 4 |
| `000401` | RX `01 10 ... payload 04` | earlier RX `01 0A`, page/index 5 |
| `000423` | RX `01 11 ... payload 05` | earlier RX `01 0C`, page/index 6 |

The recorder then returns RX `01 12 ... payload 06`, followed by RX `01 13`.
This request/reply progression is evidence of an indexed write operation, not
seven unrelated messages.

## Per-write derivation

### `000301` - 13-byte `01 0C` acknowledgement

TX is exactly:

`01 0C 00 01 01 01 02 01 02 0C 03 0C 04`

It is generated by the same rule as the earlier acknowledgements for RX `01 02`,
`01 04`, `01 06`, `01 08`, and `01 0A`:

- frame offsets `0x000`, `0x008`, `0x00A`, `0x00C` are framing;
- offsets `0x001` and `0x009` copy the RX transaction (`0C`);
- offset `0x005` copies RX offset `0x004` (`01` here);
- offsets `0x002`, `0x003`, `0x004`, `0x006`, `0x007` are constants proven by
  all six acknowledgement messages;
- offset `0x00B` is the payload sum, therefore `0C`.

Every byte is explained. This message is best classified as a harmless
acknowledgement/transition, not a configuration payload. It is nevertheless not
sent by application code because it immediately enters the unsafe indexed-write
phase and the task explicitly prohibits sending these writes to hardware yet.

### `000312` - page 1, 0x10B bytes

Source is the earlier RX `01 02` page. Its 255-byte payload is transformed as
follows (ranges are end-exclusive):

| Source RX payload | Target TX payload | Result |
|---|---|---|
| `0x00..0x05` = `06 00 00 05 C0` | `0x00..0x01` = `02` | unexplained replacement |
| `0x05..0x86` | `0x01..0x82` | copied |
| `0x86` = `04` | `0x82` = `FA` | modified; rule/meaning unknown |
| `0x87..0xB8` | `0x83..0xB4` | copied |
| `0xB8` = `00` | `0xB4` = `03` | modified; rule/meaning unknown |
| `0xB9..0xFF` | `0xB5..0xFB` | copied |
| no source | `0xFB..0xFF` = four `00` bytes | unknown padding/content |

This gives 248 LCS-copied payload bytes and seven unexplained/modified TX bytes.
The unexplained full-frame TX offsets are `0x009`, `0x08B`, `0x0BD`, and
`0x104..0x107`. The earliest safety blocker is `000312` offset `0x009` (`02`).

The payload visibly contains recorder identity/configuration material including
`V02.04_`, `05C077`, `79804`, and `171804`. Those values also occur in the
existing `TestData/CLASS171_GUI_TEST.ccf`; the longest exact contiguous CCF match
is 124 bytes, and 244/255 bytes match the most plausible contiguous CCF page
position. This is strong evidence of a configuration structure, not a temporary
session token.

### `000401` - page 5, 0x10B bytes

Source is RX `01 0A`. All 255 payload bytes are copied exactly; in this capture
they are all zero. Only the framing/header role changes from read transaction
`0A`, page/index `05`, to write command/page `05`. The check is the proven
payload sum (`00`). Every byte of this one message is explainable, but it is page
5 of the same gated six-page write operation. It is not independently safe to
send or evidence that the operation is session-only.

### `000423` - page 6, 0xD2 bytes

Source is RX `01 0C`, whose payload is 202 (`CA`) bytes. The TX payload is 198
(`C6`) bytes:

| Source RX payload | Target TX payload | Result |
|---|---|---|
| `0x00..0xC4` | `0x00..0xC4` | 196 bytes copied |
| `0xC4..0xC9` = five `00` bytes | `0xC4` = `40` | unexplained 5-to-1 replacement |
| `0xC9` = `00` | `0xC5` = `00` | copied |

The payload sum correctly produces the observed check `40`, but that does not
explain where the payload byte `40` comes from. Its full-frame TX offset is
`0x0CD`. The changed length at frame offset `0x007` follows from the shorter
payload, but the rule that selects/removes these four bytes is also unproven.

## Safety/persistence assessment

`000301` is a harmless acknowledgement/transition by payload transformation.
The other messages are indexed writes of recorder-derived configuration pages.
They are not harmless echoes: pages 1-4 and 6 delete, insert, or modify payload
bytes, and the recorder acknowledges each page before Analyser sends the next.

The capture does not include a power cycle or a post-write read-back, so it does
not prove whether these pages are committed persistently or are temporary
live-session working configuration. It also cannot prove whether the unexplained
`40` in `000423` is a session flag or configuration data. Because identity and
configuration structures are present and the operation is explicitly an indexed
write sequence, pages `000312` through `000423` must be treated as potentially
persistent recorder configuration/programming.

The existing source documentation provides no protocol definition for message
types `01 0C` through `01 13`. `README.md` explicitly excludes Program OTMR,
configuration writes, and unidentified commands; `docs/OTMR_DATABASE_AND_SERVER_SYNC.md`
defines CCF as logical OTMR configuration and SQLite as capture/history storage.
No project evidence changes the conservative classification above.

## Implementation decision

`OtmrProtocolDerivation` implements only rules for which every generated byte is
proven: payload-sum validation, the current-recorder-derived 13-byte read-data
acknowledgement (including `000301`), and the exact-copy page-5 transformation
for `000401`. Tests reproduce all six captured read-data acknowledgements,
`000401` from the current RX `01 0A` page, and every listed page transformation.
Neither generator is connected to the hardware live-start service.

No generator was implemented for `000312`, `000335`, `000357`, `000378`, or
`000423`, because the overall indexed operation still contains
unexplained safety-critical bytes. The first preventing offset is `000312` frame
offset `0x009`; later blockers are listed above. `RecorderConfigurationWriteBlocked`
remains in place, none of these seven messages is sent to hardware, and hardware
live-start cannot yet safely proceed.
